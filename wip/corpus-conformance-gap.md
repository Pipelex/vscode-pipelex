# What the vendored corpus is checked for here, and what it still isn't

Recorded 2026-08-20 from the code review of the corpus vendoring change on `feature/MthdsTestCorpus`, revised twice in that review, and **substantially closed on 2026-08-21** when `pipelex` v0.51.0 shipped the signal the partition was waiting on. What is left is the semantic half, which this toolchain structurally cannot do.

## What parity proves, and what it does not

`crates/pipelex-cli/tests/parity.rs` formats and lints every fixture through the in-process `pipelex_tools` library and through the shipped `plxt` binary, and requires the two to agree. Both sides are **the same Rust engine**, in two embeddings. So parity proves the library and the binary do not drift — a real property, now checked over a much larger and independently-owned body of MTHDS than this repo authors — but it says nothing about whether the engine's verdict is *correct*.

That was measured, not assumed. Two identical **non-empty** diagnostic sets satisfy the equality assertion exactly as well as two empty ones, so parity stays green over content the toolchain rejects, provided it rejects it the same way twice. `test-data/mthds/` demonstrates it in the repository as it stands: most of those fixtures are curated bad MTHDS that `plxt lint` rejects, and parity is green over all of them. A raw TOML syntax error is weaker still — `format_matches_cli_on_every_fixture` hits its `continue` and asserts nothing at all for that fixture.

## Closed: the structural partition, on `fails_at` — 2026-08-21

`crates/pipelex-cli/tests/corpus.rs` no longer holds every entry to one unconditional expectation. It reads each entry's `covers` list and the vendored `vocabulary.toml`, and holds the entry to whichever expectation the corpus itself declares: a diagnostic is **required** when a covered `error.*` tag carries `fails_at = "schema"`, and **forbidden** otherwise.

That closes the failure the vendoring exists to catch, in both directions. Strict-to-permissive was already covered: a stale `mthds.schema.json` that stopped accepting the canonical corpus goes red in the commit that syncs it. Permissive-to-strict is the new half, and nothing else in this repo covers it — a schema that quietly stopped *rejecting* an unknown pipe type, or a key it does not allow, leaves every valid entry green, so the schema-fault entries are the only probes for it.

**The signal is `pipelex`'s, not this repo's.** `fails_at` is generated upstream from the validation-error-type registry and travels in `vocabulary.toml`, so a fault moving between layers arrives with the next sync instead of needing an edit here. That was the whole point of settling it with `pipelex` rather than deciding it locally, and it is why the two partitions this note previously argued about are both dead:

- **`validity` is the wrong axis.** It is a *semantic* declaration — what the `pipelex` runtime makes of the bundle — while `plxt lint` is structural: TOML syntax, then DOM validation, then JSON Schema, with references never resolved. The two axes cross rather than nest. "invalid ⇒ require a diagnostic" goes red on the great majority of invalid entries, whose faults (unresolved concepts, missing or extraneous input variables, unguarded optionals) are invisible to a structural check; "invalid ⇒ skip" throws away the handful whose fault *is* structural, which are exactly the permissive-direction probes.
- **Deriving the layer from the error type's name is the wrong method**, even where it would give the right answer. It is a second reading of `pipelex`'s registry, invented downstream and free to drift from it silently.

Measured on 2026-08-20 against `pipelex` commit `3361711a7`, and re-confirmed on 2026-08-21 against the v0.51.0 sync: all invalid entries lint clean here except `invalid_unknown_pipe_type` (`"PipeWondrous" is not one of [...]`, at `pipe.write_catalog_line.type`) and `invalid_missing_pipe_type` (`Additional properties are not allowed ('prompt' was unexpected)`, at `pipe.write_round_sheet`). Both are `error[schema]` and both are exactly the two the vocabulary marks `fails_at = "schema"` — the registry-derived signal and this toolchain's own behaviour agree, which is the property that makes the gate meaningful rather than circular.

The gate was verified live rather than assumed: flipping `error.unknown_pipe_type` to `fails_at = "runtime"` in the vendored copy turns the suite red naming that entry, and the copy was restored to byte-identical afterwards. The suite also refuses to pass vacuously at every step — empty discovery, a vocabulary classifying no schema fault, a schema fault the slice carries no entry for, an unrecognised `fails_at` value, a covered `error.*` tag the vocabulary does not classify, and a tag declaring neither `fails_at` nor an `excluded` reason are each a failure rather than a lenient default.

The last two arrived from the PR review and are worth keeping straight, because both mirror an invariant `pipelex` already enforces at the source (`tests/unit/pipelex/test_extras/test_mthds_corpus_exhaustivity.py`: every non-excluded tag is owed a focused entry, and every tag so owed must name its layer). Restating them downstream catches something upstream's gate structurally cannot — a **partial sync**, where the vendored vocabulary and the vendored entries come from different versions. The per-fault form matters: checking that *some* entry probed *some* schema fault leaves the two existing probes holding the count above zero while a newly declared fault arrives with no entry, so the rejecting direction goes unchecked for precisely the fault that just changed. Both were verified by hand-editing the vendored copy until each went red naming the offending tag, then restoring it byte-identical.

**When re-measuring by hand, run from outside the repo root, or drive `plxt` on stdin with `--no-auto-config`.** `plxt.toml` excludes `test-data/**`, so pointing the CLI at those paths from the repo root reports `found files total=1 excluded=1` and exits **0** having linted nothing — a false clean that looks exactly like a pass.

## The half that remains, and why this toolchain cannot do it

What is still missing is the actual cross-language *semantic* conformance check: does a second, independent implementation of MTHDS agree with the canonical set's own declared verdicts?

`plxt lint` cannot answer that, and the reach of the gap is worth stating precisely, because the obvious framing overstates what is achievable here. Linting never resolves references. A corpus bundle whose `output` names a concept that exists nowhere in the bundle lints **clean, exit 0**. So structural acceptance is the ceiling of what this repo can check on its own, and the `fails_at` partition above is exactly that ceiling made explicit rather than a step toward crossing it.

Agreement with `expected_error` is further out still. That field names a `pipelex` runtime `error_type`, produced by loading and dry-running a bundle, which is a Python-side capability with no counterpart in this toolchain. **It belongs in `pipelex` or in `conformance/`, not in a Rust crate with no semantic layer to compare against** — and `conformance/` already does it, driving the real `/validate` wire over the same `validity = "invalid"` slice. There is consequently nothing queued for this repo here; this section records where the work lives, not work waiting on us.

The separate question of whether the vendored copy is still byte-identical to upstream is **not** part of this gap and is not this repo's to answer: the workspace-root `docs/specs/mthds-test-corpus.md` assigns it to the workspace-side `mthds-corpus-sync` sweep, because a consumer's CI only ever checks out one tree. Automating that sweep is tracked in the workspace's `wip/corpus/automating-the-corpus-freshness-sweep.md`.
